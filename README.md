### 2. Анализ архитектуры монолитного приложения

Перечислите здесь основные особенности текущего приложения: какой язык программирования используется, какая база данных, как организовано взаимодействие между компонентами и так далее.

- Язык программирования:
  - Go – высокопроизводительное, компилируемое, статически типизированное приложение.
- База данных:
  - PostgreSQL – основное хранилище данных (пользователи, дома, устройства, датчики, измерения температуры, команды управления, журналы).
- Архитектура:
  - Монолитное приложение – вся логика (обработка HTTP‑запросов, бизнес-правила, доступ к данным) находится в одном исполняемом сервисе. 
  - Внутри монолита — логические модули (пакеты Go) для разных областей: пользователи, устройства, отопление, мониторинг температуры и т.д.
- Взаимодействие компонентов:
  - Синхронное взаимодействие: модули вызывают друг друга напрямую как функции/методы (без сетевых вызовов между ними). 
  - Общая БД: все модули работают с одной базой PostgreSQL, часто через общие слои репозиториев/DAO. 
  - Обработка запросов: входящий HTTP‑запрос → маршрутизатор → обработчик → бизнес‑логика → доступ к данным → ответ.
- Масштабируемость:
  - Масштабирование по схеме «несколько одинаковых экземпляров монолита за балансировщиком». 
  - Нельзя независимо масштабировать отдельные части (например, только обработку телеметрии, не трогая веб‑интерфейс).
- Развёртывание:
  - Для выката новой версии нужно пересобрать и перезапустить весь монолит. 
  - Даже изменения в одной области (например, в отчётах) требуют перезапуска приложения целиком.

### 3. Определение доменов и границы контекстов

Опишите здесь домены, которые вы выделили.

- Домен «Управление устройствами» (Device Management)
  - Описание: инвентаризация и жизненный цикл физических устройств (котлы, клапаны, контроллеры, датчики температуры) и их привязка к домам/комнатам.
  - Типичные сущности: Устройство, Дом, Комната, Датчик, Связка дом–устройство.
  - Граница контекста: отдельный модуль/пакет в монолите (например, internal/devices), предоставляющий API для других контекстов
    - «Список устройств пользователя», 
    - «Зарегистрировать новое устройство», 
    - «Обновить статус устройства».
- Домен «Управление отоплением» (Heating Control)
  - Описание: бизнес‑правила включения/выключения отопления, выбор режимов, обработка команд пользователей и автоматических сценариев. 
  - Типичные сущности: Команда управления, Режим работы (ручной/авто), Зона отопления, Сценарий отопления. 
  - Граница контекста: модуль (например, internal/heating), который принимает команды с UI, использует Управление устройствами для получения целевых устройств и Мониторинг температуры для принятия решений.
- Домен «Мониторинг температуры» (Temperature Monitoring)
  - Описание: приём, хранение и предоставление температурных данных с датчиков. 
  - Типичные сущности: Измерение температуры, Датчик, Агрегированная метрика (средняя/мин/макс). 
  - Граница контекста: модуль (например, internal/temperature), который:
    - принимает входящие данные от датчиков, 
    - валидирует и сохраняет их в БД, 
    - отдаёт данные другим доменам и пользователям через запросы.
- Домен «Пользователи и доступ» (User Management & Access)
  - Описание: управление учётными записями и правами на дома/устройства. 
  - Типичные сущности: Пользователь, Роль, Сессия/Токен. 
  - Граница контекста: модуль (например, internal/users), к которому обращаются все остальные:
    - проверка аутентификации, 
    - проверка, кому принадлежат дом/устройство, 
    - управление профилем.
- Дополнительные домены (по необходимости)
  - «Уведомления» – отправка предупреждений при выходе температуры за пороги или сбоях устройств. 
  - «Отчёты и аналитика» – построение агрегированных отчётов и графиков по истории.

  Все эти домены — логические bounded context’ы внутри одного монолита, что упрощает последующий переход к микросервисам (каждый контекст можно выделить в отдельный сервис).

### **4. Проблемы монолитного решения**

- Ограниченная масштабируемость по частям 
  - Нельзя независимо масштабировать разные нагрузки:
    - поток телеметрии от датчиков может расти гораздо быстрее, чем нагрузка веб‑интерфейса, 
    - но масштабируется всегда весь монолит целиком, что неэффективно по ресурсам.
- Сложность и риск развёртывания 
  - Любое изменение (даже в одном домене) требует выпуска и перезапуска всего приложения. 
  - Это увеличивает риск регрессий и время простоя при обновлениях (если нет безdowntime‑стратегий раскатки). 
- Сильная связанность модулей 
  - Со временем модули (управление устройствами, отопление, мониторинг, пользователи) начинают активно зависеть друг от друга, 
  - нарушаются границы контекстов, появляется «спагетти» из зависимостей, что усложняет развитие и рефакторинг. 
- Снижение скорости разработки при росте команды 
  - Большой общий код (один репозиторий, один бинарник, общие модели) затрудняет параллельную работу разных команд. 
  - Любое изменение требует знания большого куска системы, растёт стоимость входа новых разработчиков.
- Технологическая негибкость 
  - Переход на другой стек (например, отдельный сервис на другом языке для анализа телеметрии) труднее, так как всё связано в один Go‑монолит. 
  - Труднее использовать разные подходящие технологии для разных задач (стриминг, очереди, отдельные хранилища для телеметрии и т.п.).

Если вы считаете, что текущее решение не вызывает проблем, аргументируйте свою позицию.

# Задание 4. Создание и документирование API

### 1. Тип API

- Синхронный REST API (HTTP/JSON)
  - Используется, когда вызывающей стороне нужен сразу результат: запросы от API Gateway к сервисам, вызовы между сервисами (Scenarios & Automation → Telemetry, Device Control, Catalog; Device Control → Catalog; Telemetry → Catalog и т.п.).
- Обоснование: клиент и оркестраторы (например, движок сценариев) не могут продолжить работу без ответа; REST по HTTP удобно описывать в OpenAPI и интегрировать в Java-стек (WebClient, OpenFeign).
- Асинхронный API (события/очереди)
  - Используется, когда ответ ждать не нужно: публикация событий (например, telemetry.measured, command.sent), несколько подписчиков, развязка по времени и нагрузке.
- Обоснование: отправитель не блокируется; пики нагрузки (телеметрия) не нагружают критичный путь; очереди (Kafka/RabbitMQ) дают буферизацию и масштабирование потребителей; контракт описывается в AsyncAPI.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql
